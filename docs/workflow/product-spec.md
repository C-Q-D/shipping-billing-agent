# 产品需求文档（PRD）：多格式文档解析的航运智能账单助手智能体

## 1. 背景与核心目标

### 1.1 要解决的问题
国际货代与航运结算场景中，费用确认高度分散在各类非结构化渠道：
- **单据格式高度异构**：业务往来同时包含 `.eml` 预配通知邮件（Pre-Alert，正文含简写扣费指令，附件携带主单 MBL、分单 HBL 与宣传签名图）、PDF 账单或到货/通用通知（含多页免责条款）、扫描图片发票、Excel 费用明细表与 Word 对账单。
- **条款噪声与 OCR 错识风险大**：通知类文档往往夹杂条件性罚金或费率条款（如取消 I.T. 服务费、空箱误还违约金、司机超时费率）与银行账号数字，且扫描件中常出现 `0/O`、`1/I`、`5/S` 混淆或边缘字符裁切，直接录入极易产生错账。
- **AR/AP 视角极易判反**：同一份 `Debit Note` 或 `Invoice`，站在签发方（如目的港代理）是应收（`AR`），站在接收方（如起运港代理）则是应付（`AP`）；贷项单据（`Credit Note`）还需明确冲减方向；邮件指令如 `SHA pay TAR: H/C $50` 更需结合附件提单还原双方主体全称。
- **更新账单与重复入账风险高**：历史账单再发或部分字段调价/改条款时，需要按业务优先级精准匹配已有记录，只更新明确要求变更的字段、继承其余字段原值后再行校验，同时把合法同单同名多行费用与重复提取区分开来。

### 1.2 核心目标
构建一个“**高可靠解析 + 确定性校验门禁 + 可追溯人工复核**”的航运智能账单助手智能体，同时提供 **Web 财务复核工作台** 与 **命令行/程序化批处理入口**。只要输入单据包、当前记账主体与（可选）已有账单 JSON，系统即可输出**可审计、可追溯、100% 合法且符合财务系统标准格式的账单 JSON**，并将重复单据、数据冲突、低置信度或主体归属不明的记录拦截至待复核队列完成人工闭环。

### 1.3 使用者与使用环境
| 使用者角色 | 典型使用场景 | 使用环境与入口 |
| :--- | :--- | :--- |
| **货代财务专员 / 结算主管** | 日常接收代理或船司发来的邮件、PDF、图片、Excel/Word 账单，核对费用、确认 AR/AP 与贷项冲减、排查差异并导出标准账单 JSON | 桌面浏览器（主流 `1280×800`）与移动巡检视口（`390×844`）下的 Web 财务复核工作台 |
| **系统集成方 / 评测与运维人员** | 批量跑通多格式单据、联调已有账单匹配逻辑、移交异常批次给财务接手，以及执行稳定性与准确率回归测评 | 本地 Python 命令行（CLI）批处理与离线 Harness 评测命令 |

| `F-07` | 命令行批处理与 Harness 离线评测套件 | 本次新增 | 提供与工作台互通复核包的 CLI 批量解析命令、内置多格式+对抗样本 Harness 评测报告，以及可直接解包运行的交付物与书面深度报告。 |

### 2.2 后续延后项（Later）
已同步记入 `docs/workflow/backlog.md`，本轮不展开操作细则：
- 直连真实 ERP/FMS（GoFreight / CargoWise / SAP）生产写入接口；
- 邮箱 IMAP/Exchange 定时自动抓单；
- 多币种实时汇率换算与月度对账单（SOA）净额核销；
- 多租户账套隔离与多级账号审批流。

### 2.3 明确不做清单（Non-Goals）
- 不执行真实资金付款、银行转账或税务电子发票开具；
- 不自建分布式公网文件存储集群（需要公网地址供外部 OCR 访问时，仅提供可配置链接或可插拔中转配置入口）；
- 不开发与账单解析、校验、复核和评测无关的通用闲聊对话模块。

## 3. 整体使用主线

为便于直观对照业务全貌与四态决策逻辑，请参阅以下两张独立交互图示：
- 端到端角色协作与人工复核回流主线：[航运账单智能处理与人工复核主流程图](diagrams/user-billing-flow.html)
- 校验门禁、四级匹配与操作类型判定流：[费用操作类型判定与校验门禁流程图](diagrams/operation-decision-flow.html)

### 主线 1：新单据投递、自动校验与直接入账（`CREATE`）
1. **入口与动作**：财务人员打开 Web 工作台，选择当前**记账主体**，拖拽上传本地多格式单据（或填写单据公网下载链接），点击**“开始智能解析”**。
2. **智能体处理**：系统按批次解包文件；若为 EML，自动提取邮件头与正文、过滤签名宣传图噪声、递归解析 PDF/Excel/Word/图片附件，并在同一批次内共享提单/箱号/交易方上下文；对 PDF 与图片调用 OCR 服务提取费用并完成多维标准化；未命中历史账单且全部确定性校验通过的条目，直接生成 `CREATE` 正常记录（多条费用分别独立成条）。
3. **可见结果与结束**：工作台实时展示解析阶段，校验通过的正常记录**无需人工逐条审批即可直接进入可导出就绪状态**；财务核对明细、AI 依据与 AR/AP 后，点击**“导出正式标准 JSON”**下载即用，流程结束。

### 主线 2：携带已有账单库投递变更/重发单据（`UPDATE` / `NO_CHANGE`）
1. **入口与动作**：财务人员导入（或选用工作台内已加载的）**已有账单基准库**，再上传新收到的变更单据（支持仅写明部分变更字段如仅改 `payment_term` 的调账通知，或重发原单），点击**“开始智能解析”**。
2. **智能体处理**：系统先识别新材料明确提供的字段，按当前记账主体限定候选并执行四级匹配（单据编号+费用名 → 提单号+费用名+币种 → 订舱号+费用名+币种 → 箱号+双方+日期+金额）。唯一命中后，未提字段严格继承原历史账单值，再对合并后的完整记录执行确定性校验：存在实质变更时输出 `UPDATE` 并生成字段前后对比；关键业务字段完全一致时输出 `NO_CHANGE` 拦截重复入账。
3. **可见结果与结束**：工作台以“变更前后高亮对比”呈现 `UPDATE` 行，以低噪状态呈现 `NO_CHANGE` 拦截行。本期默认采用**显式导入/工作台账单库基准**以保证重放与评测可复现；财务可按需显式点击“将本批已确认记录同步到工作台历史库”，之后再次投递同一单据即可识别为 `NO_CHANGE`，流程结束。

### 主线 3：文件失败、校验异常、多候选冲突的人工复核闭环（`PENDING_REVIEW`）
1. **入口与动作**：当出现以下任一异常——① 某文件/附件解析或 OCR 完全失败（即使未产出费用行）；② 行明细求和（含税/小计/明确零总额）与总计不平；③ OCR 疑似 `0/O`、`1/I` 或字符格式存疑；④ EML 正文与附件跨文档冲突或提单号跨来源不一致；⑤ 当前记账主体归属不明；⑥ 匹配到多条不同历史账单无法唯一消歧；⑦ 同批次双入口上传同一单据需归并——系统将问题精准落到受影响记录或**文件级失败告警卡**，费用条目强制标为 `PENDING_REVIEW`。
2. **人工介入与恢复**：财务人员点选**“待复核”**或顶部失败文件告警卡，即可看到“哪份文件未读到、哪些费用受其上下文影响”，支持直接**单文件重试/替换**（保留同批其余成功结果）；针对费用级待复核记录，财务可对照原文片段与告警就地补全/修订字段、点选关联哪条历史账单、补充漏提费用行、带理由确认原文特例，或点击**“驳回排除”**。
3. **状态闭环与结束**：保存修订或替换重解后，系统即时重跑匹配与确定性校验（人工已锁定修订的字段不会被原文件原文自动覆盖）；通过后条目自动转入对应终态并可纳入正式导出（被驳回项保留在审计日志中、自动从正式账单 JSON 排除），流程结束。

### 主线 4：命令行批量执行、跨端复核接手与 Harness 评测
1. **入口与动作**：集成或评测人员在终端执行 CLI 批处理命令（传入输入路径、记账主体、已有账单基准、输出路径）或 Harness 评测命令。
2. **系统处理与可见结果**：CLI 打印每个文件的状态计数与结果摘要，输出标准 JSON 文件，并同时生成可直接导入 Web 工作台（或存入本地共享批次列表）的**复核包文件**。当存在失败文件或待复核条目时，财务可凭终端提示的短批次号或导入该复核包，在 Web 工作台打开原件溯源与告警接手处理；评测命令则输出字段准确率、`pass@k` / `pass^k` 与冲突拦截率报告，以退出码明确指示通过与否。

## 4. 逐功能操作流程与状态细则

### F-01 多格式单据投递与递归解析

1. **入口与前置条件**：
   - 入口 A：Web 工作台首屏左侧输入区（无需登录，空态直接可见投递区与内置样例加载按钮）及顶栏“导入 CLI 复核包 / 切换历史批次”菜单。
   - 入口 B：CLI 命令传入单文件、文件夹、公网 URL 列表或已保存复核包。
   - 前置条件：选定或输入至少 1 个待解析单据（本地文件或公网 URL）与当前记账主体名称。
2. **分步操作与输入要求**：
   - **步骤 1（选择单据来源，必填，至少一项）**：
     - 本地文件上传/拖拽：支持 `.eml`、`.pdf`、`.jpg`、`.jpeg`、`.png`、`.tif`、`.tiff`、`.xls`、`.xlsx`、`.doc`、`.docx`（单文件 ≤ 50 MB，单批 ≤ 50 个文件）；无需预先在运行环境安装桌面 Office 套件即可直接解析旧版 `.doc`/`.xls` 与新版 `.docx`/`.xlsx`。
     - 公网文件 URL 列表（选填，多行文本）：用于直接向指定 OCR 网关投递可公网下载的 PDF/图片地址，须以 `http://` 或 `https://` 开头。
     - 已有账单基准 JSON（选填）：支持上传 `.json`、在抽屉粘贴文本或选用工作台内已保存的账单库（顶层为数组或包含账单数组的对象）。
     - 快捷示例包（选填）：首屏空态提供“一键载入笔试样本包（4 份真实单据）”按钮。
   - **步骤 2（外部 OCR 与本地文件策略）**：
     - 对公网 URL 或配置了可访问公网中转地址的文件，直接投递至指定 OCR 服务；
     - 对本地上传的二进制 PDF/图片且当前未配置公网中转地址时，界面清晰提示“本地文件无法被远端 OCR 服务端直接下载”，允许用户填配公网中转地址，或显式勾选**“本地安全兜底解析（明确标注解析来源并进入校验/复核提示）”**；绝不静默伪造远端 OCR 成功。
   - **步骤 3（触发解析）**：点击主按钮**“开始智能解析”**。
3. **正常反馈与去向**：
   - 主按钮即时置灰防连点，顶部阶段进度条逐步点亮：`收件拆包 → 多模态提取 → 匹配与继承 → 校验门禁 → 结果就绪`。
   - 对 `.eml`：完整解析邮件头（主题、发件人、收件人、抄送、日期）、纯文本与 HTML 正文并递归解包全部附件（自动清洗文件名中如不换行空格等异常空白字符）；正文 HTML 中通过内容标识引用且位于邮件签名区的宣传/二维码图（如 `InsertPic_C25B.jpg`）自动标为“已跳过（邮件签名/装饰图）”留在附件树，用户可随时点击“强制纳入解析”推翻。
   - 同封 `.eml` 及其内部附件绑定至同一“单据上下文包”，允许正文简写指令（如 `SHA pay TAR: H/C $50`）关联附件 MBL/HBL 中的主体全称、提单号与预付/到付属性。
   - 对 `.xls`/`.xlsx`：逐表扫描，自动定位表头行、向下填充合并单元格并记录工作表名与行号。
   - 对 `.doc`/`.docx`：按阅读顺序提取段落、抬头与全部表格行列。
4. **边界、异常与多区域联动状态**：
   - **首次 / 空数据态**：工作台首屏保持紧凑布局，输入投递区与操作引导同屏可见，不出现巨幅留白将核心按钮挤出视口。
   - **输入不合规**：扩展名不支持、0 字节空文件、损坏 JSON 或非法 URL 在对应输入项下方即时显示红色人话报错并拦截提交；用户修正或移除坏文件后报错即时清除。
   - **单文件或单附件完全失败（含 0 费用产出情形）**：若某图片 OCR 超时/报错或某 PDF 加密损坏导致未能提取任何费用，系统**绝不能因费用列表为空而静默跳过**：必须在文件树标红失败原因，并在中栏顶部显著展示**文件级失败告警卡片**（注明失败文件名、错误原因及同邮件中依赖该附件的关联费用项），提供**“原地重试该文件”**或**“上传替换附件并重算关联费用”**动作；同批其余正常文件与费用照常产出，批次统计明确分开显示“成功文件数 / 失败文件数 / 生成账单数 / 待复核数”。

### F-02 航运账单信息提取与多维标准化

1. **入口与前置条件**：
   - 由 `F-01` 产出各文档原始内容与 OCR 结果后自动执行；词典配置抽屉支持查看与增删费用名称映射。
2. **分步操作与输入要求**：
   - **单据元信息与多源业务标号提取**：
     - 识别 `document_type`（`Debit Note`、`Credit Note`、`Invoice`、`General Notice`、`Arrival Notice`、`Bill of Lading`、`Email Instruction` 等）、`reference_no`（无显式独立账单号时留 `null`，不得把提单号直接冒充账单号；若原单明确以 B/L 作为发票参考号，则在依据中注明）、`document_date`（统一格式化为 `YYYY-MM-DD`，无法确定或无有效日期时填 `null`）。
     - **多源提单/订舱/箱号保留与溯源**：当同一上下文包内多个文件出现不同或略有差异的提单标号（例如邮件正文写 `MBL NO.: OOLU4055331281`、HBL `EXPORT REFERENCES` 写 `OOLU4055331281`，而 MBL 附件原件印 `B/L NO: HZMHK331281` 与 `BOOKING NUMBER: 4055331281`）时，系统必须**保留全部原始标识并附上各自来源标签**，不得丢失其一；若无法确认两者是否属于同一主单映射（如 SCAC 前缀 + 订舱号 vs 货代 MBL 号），在证据与告警区主动提示财务核对。
   - **交易双方提取**：识别 `issuer` 与 `recipient`；针对邮件简写（如 `SHA pay TAR`），仅在同封邮件/附件中能找到有依据的对应实体时（如起运港 `SHA` 对应起运地出单方 `SUN TRACK EXPRESS`、`TAR` 对应目的港收货/代理 `TARGETING A INC`）才作关联映射并在 `ai_reasoning` 逐字写出推导依据；缺乏依据时保留原始简写并交由主体核对。
   - **费用明细行提取与防幻觉约束**：
     - 逐行提取 `raw_charge_name`、`quantity`、`unit_price`、`amount`、`currency`、`payment_term`、所在页码/行号、借贷列方向（`DEBIT(+)` / `CREDIT(-)`）。
     - **严格遵守不编造原则**：缺失字段一律填 `null`（例如 `WHARFAGE` 仅印出计费基数 `PTT`、费率 `2.85` 与金额 `21.90`，未印出数量时，`quantity` 必须为 `null`，禁止用金额反除单价造出小数数量）。
     - **币种与付款方式可信依据边界**：
       - 仅出现 `$` 符号时：若文档上下文（如美国目的港/起运方惯用美元或同单其余明确写 `USD`）有充分佐证，可规范为 `USD` 并在 `ai_reasoning` 标注“由 `$` 符号及同单/美线上下文推导出 `USD`”；若上下文多币种混杂或无法确认是 `USD`/`CAD`/`AUD`/`HKD`/`SGD`，填 `null` 并标待复核；
       - 付款方式：仅当费用行自带 `P`/`C`/`PP`/`CC`/`Prepaid`/`Collect` 列标识，或同单明确声明全单运费/费用均为 `FREIGHT PREPAID`/`FREIGHT COLLECT` 时，才能填充 `PP`/`CC` 并在 `ai_reasoning` 写明具体出处；若原文仅针对海运费写 `FREIGHT PREPAID` 而本地代理操作费（如 `SHA pay TAR: H/C $50`）本身未指明 `PP/CC`，可继承标为 `null`（或给出清晰依据标识并提示财务确认），**绝不允许靠猜强填确定值**。
     - **排除非计费条款与免责声明**：自动过滤通用通知中的条件性违约金/费率条款（如 General Notice 第 1~3 页 `$25.00 per cancelled I.T.`、`$1100` SOC 误还箱罚金、`$150/hr` 司机等待费率）、银行汇款账号以及免费豁免项（如 `Carrier Free H/C`），仅在右侧“已排除非计费条款”区列示说明供复核。
   - **费用名称标准化**：同时保留 `raw_charge_name` 与映射后的 `charge_item`，内置并可扩展覆盖题设标准映射（`Handling Fee`/`H/D Fee`/`H/C`/`HANDLING CHARGE` → `Handling Charge`、`Doc Fee` → `Documentation Fee`、`THC` → `Terminal Handling Charge`、`Trucking Fee` → `Trucking Charge`、`Customs Fee` → `Customs Clearance Fee`、`Storage Fee` → `Storage Charge`、`WHARFAGE` → `Wharfage`、`WHARFAGE ADMINISTRATION FEE` → `Wharfage Administration Fee`、`4 ADD'L DETENTION FREE TIME CHARGE` → `Detention Free Time Charge`、`On Carriage Additional - US Em` → `On Carriage Additional` 等）。
3. **正常反馈与去向**：
   - 每个有效计费项目独立输出一条记录；单据小计（Subtotal）、税额（Tax）与总计（Total）随同单据上下文进入后续匹配与对账门禁。
4. **边界、异常与多区域联动状态**：
   - 纯运输单据且无计费金额（如单独上传 `MBL.pdf` / `HBL.pdf`）时，文件树标为“仅运输单据元数据（无计费项目）”，不生成 0 元账单。
   - 词典管理允许财务增改别名映射并触发“仅重新标准化当前批次”，未保存编辑切换弹框时给出提示。

### F-03 记账主体视角管理与 AR/AP 智能判定

1. **入口与前置条件**：
   - 入口：工作台左侧/顶栏“当前记账主体”选择器（支持常用主体快速选择、自定义名称输入及别名列表维护；CLI 通过参数传入）。
   - 前置条件：已提供当前记账主体名称。
2. **分步操作与输入要求**：
   - **配置记账主体（必填，1~120 字符）与别名（选填）**：支持配置规范名称及英文缩写、中文名称、分支抬头等别名（如 `NEPTUNE SHIPPING LIMITED` 别名 `NEPTUNE SHIPPING LIMITED (LAX)`；`SUN TRACK EXPRESS (CHINA) CO., LTD.` 别名 `Origin Agent, SHA, 深圳容宇`；`TARGETING A INC` 别名 `Destination Agent, TAR`）。
   - **综合判定逻辑（单据类型 + 双方角色 + 借贷方向 + 记账主体）**：
     - 第一步识别资金方向与单据性质：
       - 正向收费单（`Invoice` / `Debit Note` / `Arrival Notice` / `General Notice` 含应付表 / `DEBIT(+)` 行）：正常表示 `issuer` 向 `recipient` 收费；
       - 贷项单据（`Credit Note` 或 `CREDIT(-)` 列行）：表示原收费方向的反向冲减/退回；
       - 邮件明确指令（如 `A pay B: Fee $X`）：`payer = A`、`payee = B`。
     - 第二步以**当前记账主体（含别名）**匹配收/付角色：
       - 正向收费时：主体 = 收款方（`issuer` / `payee`）→ `AR`（正金额）；主体 = 付款方（`recipient` / `payer`）→ `AP`（正金额）。
       - **贷项冲减表达（已裁决标准约定）**：保留交易主体对应的原始应收/应付台账归属，同时使用**带负号的金额数字（如 `-40.00`）**直接表达余额冲减，并在 `ai_reasoning` 明文标注“贷项冲减：对应台账余额减少 40.00”。即：主体 = 签发 `Credit Note` 方（原收费 `issuer`）→ `posting_type: "AR"`、`amount: -40.00`；主体 = 收到供应商 `Credit Note` 方（原付款 `recipient`）→ `posting_type: "AP"`、`amount: -40.00`。这样下游财务系统对同一账套直接按 `posting_type` 汇总 `SUM(amount)` 时，余额精确减少 40，无任何歧义！
     - 第三步**角色缺失/单方空白拦截**：若单据仅标明了收款方而未写明付款方（例如 `DC-108478` 仅明确 `GRAND TOTAL BALANCE DUE TO NEPTUNE SHIPPING LIMITED (LAX)`，未指明哪个具体代理为付款方，虽列有 Shipper/Consignee 但无法作为账单付款主体），则当记账主体设为 `NEPTUNE SHIPPING LIMITED` 时明确判为 `AR`，而当记账主体设为其他未在单据中被明确指定为付款方的公司时，**严禁把 Consignee/Shipper 硬猜成付款人**，必须判为 `posting_type: null` 并拦截为 `PENDING_REVIEW`。
3. **正常反馈与去向**：
   - Web 工作台在切换“当前记账主体”后，立即重算当前批次所有记录的 `posting_type`、对应主体限定下的历史账单匹配结果及统计汇总。
4. **边界、异常与多区域联动状态**：
   - **切换主体时的历史匹配与批准态重置保护**：历史账单候选检索受当前记账主体范围约束。若财务人员在主体 A 下已手动关联某条旧账单或点选了“人工批准”，随后把当前记账主体切换为主体 B：系统**不得沿用主体 A 的历史关联和批准结论**，必须自动清除跨主体失效的历史绑定与人工批准态（保留用户手改的原始单据基础字段草稿并在顶部明确提示“记账主体已切换为 B，N 条记录已重新匹配并重置原主体批准状态待核”），彻底防止跨公司账套错账。

### F-04 已有账单四级匹配与四态增量决策

1. **入口与前置条件**：
   - 紧接 `F-02` 基础字段抽取及 `F-03` 主体映射后执行（先匹配、继承合并，再执行完整 `F-05` 校验门禁，确保“仅修改付款方式等部分字段的增量更新通知”不会被漏传金额先期误拦）。
2. **分步操作与输入要求**：
   - 当未载入已有账单库时，未命中基础错误的有效费用直接拟定为 `CREATE`，进入 `F-05` 完整校验。
   - 当已载入已有账单库时，**仅在当前记账主体归属的已有账单范围内**按严格四级优先级依次查找候选：
     - **第 1 级**：`单据编号 (reference_no) + 标准化费用名称 (charge_item)`；
     - **第 2 级**：`提单号 (mbl_no 或 hbl_no) + 标准化费用名称 + 币种`；
     - **第 3 级**：`订舱号 (booking_no) + 标准化费用名称 + 币种`；
     - **第 4 级**：`箱号 (container_nos 有交集) + 交易双方 (issuer & recipient 归一化一致) + 单据日期 + 金额`。
   - **匹配候选分流与增量继承规则**：
     - **0 候选**：按新增费用处理（补全后跑 `F-05` 完整校验，通过则输出 `CREATE`）。
     - **唯一候选（或明确一对一配对的多行同名费用）**：
       - 将本次新提取的**非空且明确要求变更的字段**覆写到原账单副本上，所有本次未提及或抽出为 `null` 的字段**严格继承原历史账单值**（绝不用 `null` 覆盖已有非空原值）；
       - 对合并后的完整记录送入 `F-05` 执行全量确定性校验；
       - 若全量校验通过：核心业务字段（金额、币种、付款方式、单据日期、交易双方、AR/AP）任一发生实质改变 → 输出 `UPDATE`（在详情区并排展示“原值 → 新值”与“保留未改原值字段列表”，且携带原历史记录标识确保导出可辨认更新对象）；若核心业务字段全部一致 → 输出 `NO_CHANGE`（拦截重复入账）。
     - **多候选冲突（一对多无法唯一消歧）**：若第 1~3 级匹配到多条不同金额或不同旧单据的候选（例如同提单号存在两笔不同日期的 `Handling Charge`），或者同一单据内两条同名费用与旧账库存在交叉歧义 → 禁止擅自挑第一条覆盖，立即拦截为 **`PENDING_REVIEW（多候选待指定目标）`**，在右栏列出全部候选历史账单（显示其业务单号、提单号、金额、币种、日期）供财务点选“更新此条”或“另建新记录”。
   - **同单合法同名多行 vs 重复提取**：对于同一单据内的合法同名多行（如 `DC-108478` 中的 `65.00` 和 `35.00` 两条 `HANDLING CHARGE`），在无历史账单时两条皆标为 `CREATE`；当历史库中已有这两条时，优先按金额精确匹配 + 行序稳定配对（若两者均有修改无法确定配对，转 `PENDING_REVIEW` 人工确认配对关系），二次重投同文档时两者一一命中输出 `NO_CHANGE`。
3. **正常反馈与去向**：
   - 中栏列表清晰呈现 `CREATE`、`UPDATE`、`NO_CHANGE`、`PENDING_REVIEW` 四种标签及命中级别徽标（`L1`~`L4` / `未匹配` / `多候选冲突`）。
4. **边界、异常与多区域联动状态**：
   - 明确区分历史基准版本：针对同一份更新输入（如将 `30.00` 改为 `40.00` 的通知），当对照“原金额 `30.00` 的旧版基准”时输出 `UPDATE`；当对照“已更新为 `40.00` 的新版基准”时输出 `NO_CHANGE`。
   - 财务在工作台显式点击**“将本批已确认记录同步到工作台历史库”**后，工作台内部历史库更新为最新确认版本（含对应版本号/时间），CLI 无状态调用则始终以命令行传入的基准文件为准。

### F-05 确定性数据校验、冲突检测与自修复门禁

1. **入口与前置条件**：
   - 任何单据/费用记录（无论是新增草稿还是 `F-04` 合并继承后的完整记录）在成为 `CREATE`/`UPDATE`/`NO_CHANGE` 终态前，**必须通过本确定性校验门禁**；未经校验的 OCR 结果绝不允许直接出库。
2. **分步操作与校验清单**：
   - **校验 1 · 数值与符号合法性**：`amount` 必须为有限数字（正向单据非贷项不允许负值，贷项单据规范为负值冲减）；`quantity`、`unit_price` 若非 `null` 须为数字；当三者俱全时检查 `quantity × unit_price` 与 `amount` 是否在容差（`±0.02`）内一致。
   - **校验 2 · ISO 4217 币种校验**：`currency` 若非 `null` 必须属于标准 ISO 4217 三位大写字母表；单据费用中未明确给出有效币种（`currency is null`）且未能从唯一上下文继承时阻断入账。
   - **校验 3 · 小计、税额、含税及零总额对账**：
     - 区分单据原始汇总行中的 **同币种未税小计（Subtotal）**、**税额（Tax）** 与 **应付/应收总计（Total / Grand Total）**；
     - 若原文同时印有 `Subtotal` 与 `Tax`：先核对 `Σ明细行 == Subtotal`（容差 `±0.02`），再核对 `Subtotal + Tax == Total`；不得把未税费用总和直接去撞含税 `Total` 而误拦合法含税账单；
     - 若原文仅印有同币种总计 `Total`（**包括明确印出的 `0.00` 零总额**，例如全额借贷互抵账单）：必须核对 `Σ明细行（含正负借贷符号） == Total`；仅当原文**完全未打印总计行**（如 EML 纯文本单行指令）时才免对账并标明“单据无汇总行”。
   - **校验 4 · OCR 易混淆字符与格式校验**：
     - 检测金额与日期串中的 `0/O`、`1/I/l`、`5/S`、多小数点（如 `1.310.40`）或非法日期；
     - 对识别出的集装箱号执行 **ISO 6346（4 位字母 + 6 位数字 + 第 11 位校验码）** 校验：若校验码不符或箱号位置出现字母/数字串混，**标为软告警并拦截为 `PENDING_REVIEW`**，提示疑似 `0/O`、`1/I` OCR 错识位及建议修正值（人工核对原图确系船司历史非标箱号时允许带理由确认通过）。
   - **校验 5 · 同单重复提取、双入口同源归并与跨文档冲突检查**：
     - **跨文档冲突**：同批次内（如 EML 正文与附件 PDF）针对同一票/同一单据同一费用给出相互矛盾的金额、币种或付款方式，或提单号存在不可解释的跨源冲突时，拦截为 `PENDING_REVIEW`；
     - **同批次双入口同源归并**：若同批次既上传了 `.eml`（内嵌某附件 PDF），又单独上传了同一份文件（内容哈希相同或同一 `reference_no + issuer + charge_item + amount + currency` 且可证属同一原始单据两份副本），仅保留 1 笔输出记录并在来源证据中同时挂载两条输入路径，绝不导出两笔 `CREATE`；而同单内多行合法费用（如 `DC-108478` 两条不同金额 `Handling Charge` 且合计等于 `1,410.40`）全数保留；
     - **超额重复提取**：若同一单据同一行被重复抽取且导致明细和超出 `Total`，立即拦截为 `PENDING_REVIEW`。
   - **校验 6 · 受控自修复回环（Self-Correction）**：当对账不平或命中确定性 OCR 格式缺陷时，向智能体反馈结构化差错原因执行**最多 1 轮带原证据复核重抽**；若重抽后全量校验通过，记录修复前后差异到 `audit_trail`；仍存在任何红灯或歧义则锁定 `PENDING_REVIEW`，禁止“凑数平账”。
   - **校验 7 · 全链路证据留存**：强制写入文件来源、页码/工作表/行号、原文摘要与 `ai_reasoning`。
3. **正常反馈与去向**：
   - 每条记录展示“校验徽章”（`校验通过` / `自修复后通过` / `N 项待复核告警`），点击告警直接定位右侧对应字段与原文档证据。
4. **边界、异常与多区域联动状态**：
   - 若同时存在多个币种且原文未按币种分列总计，系统按同币种各自校验，无单币汇总时标明“多币种分列明细”避免跨币种乱相加。

### F-06 财务复核工作台、人工裁决与标准 JSON 导出

1. **入口与前置条件**：
   - 浏览器访问工作台首页即进入（无登录门槛）；刷新页面后可从本地持久化记录中直接恢复最近工作批次。
2. **分步操作与界面信息架构**：
   - **单行紧凑顶栏（≤ 56px）**：包含系统名、批次切换器（短批次号如 `B-1119-01` ＋ 状态摘要）、当前记账主体切换器、内置基准评测入口及导出按钮组。
   - **首屏三栏工作台（`1280×800` 全屏锁高、各栏独立滚动、无双滚动条；`390×844` 窄屏折叠为紧凑标签页，输入与操作按钮零滚动可达）**：
     - **左栏（投递与上下文文件树）**：文件上传区、公网 URL 折迭输入框、已有账单上传/样例切换、“开始智能解析”按钮，以及**文件树（标注 EML 正文、附件、已跳过签名图、仅元数据单据、失败告警状态及单文件重传入口）**。
     - **中栏（批次健康提示 + 阶段进度 + 分状态列表）**：顶部紧凑阶段进度条；若有文件/附件解析失败，置顶展示可点击**文件级失败告警卡片**；下方提供 `全部`、`待复核 (N)`、`新增 CREATE`、`更新 UPDATE`、`无变更 NO_CHANGE`、`已驳回 (M)` 筛选标签，每行卡片仅显示人类业务字段（标准费名/原名、金额（含负号贷项标识）与币种、PP/CC、AR/AP、操作状态、单据号/提单号），**主界面严禁裸露长 UUID/哈希 ID**。
     - **右栏（单条/单文件详情、溯源与人工裁决区）**：
       1. **AI 推理依据与校验告警卡片**：逐条列出 `ai_reasoning`、匹配级别与具体字段错误原因；
       2. **UPDATE 前后差异对比区**：并排高亮变更字段与继承保留的原值字段；
       3. **原文溯源与已排除条款区**：显示来源文件名、页码/行号、命中的原始文本片段，以及同文档被排除的非计费条款摘要（防止误删漏提）；
       4. **全维度人工复核表单**（确保每一种阻断都能在此直接修复关闭）：
          - 支持修订：`charge_item`（标准名）、`amount`、`currency`、`payment_term`、`posting_type`、`reference_no`、`document_date`、`issuer`、`recipient`、`mbl_no`/`hbl_no`/`booking_no`/`container_nos`；
          - 支持**从候选列表点选关联历史账单**（当处于“多候选冲突”时，列出候选旧账单业务摘要供单选绑定或选“新增独立一笔”）；
          - 支持在同单漏提费用行时点击**“从该单据补充一条费用行”**；
          - 动作按钮：**“保存修订并重验”**、**“确认原文特例并批准（仅对软告警有效，硬性数值/平账红灯不可跳过）”**、**“驳回排除”**（带二次确认气泡，禁止无确认误删）。
   - **双口径标准 JSON 与审计导出**：
     - **导出正式标准 JSON（默认主按钮）**：仅包含合规可入账终态（`CREATE` / `UPDATE` / `NO_CHANGE`，人工修订批准后归入对应终态），**自动排除 `REJECTED` 及未解决的 `PENDING_REVIEW`**；点击后先在弹窗/确认条明确显示“本次将导出 `X` 条正式记录，自动排除 `Y` 条待复核与 `Z` 条已驳回”，确认后下载或复制，且保证 100% 符合题目第 5 节 JSON 结构。
     - **导出四态全量标准 JSON（评测/全状态查看）**：严格按第 5 节标准字段格式导出包含 `PENDING_REVIEW` 在内的全量非驳回记录。
     - **导出完整审计版 JSON**：保留全部标准字段外加 `source_evidence`、`validation_results`、被排除条款与 `human_review` 变更历史（含 `REJECTED` 记录及原因）。
     - **同步到工作台历史库按钮**：允许财务一键将当前已确认的 `CREATE`/`UPDATE` 写入工作台历史账单库作为后续批次对账基准。
3. **正常反馈与去向**：
   - 中栏切换焦点记录时，右栏立即切换上下文并**把右栏滚动条复位到顶部**；保存修订后，中栏卡片、计数器、导出预览与 `ai_reasoning` 实时同步更新。
4. **边界、异常与多区域联动状态**：
   - **独立草稿隔离**：在记录 A 编辑但未保存时切换到记录 B，系统独立保留 A 的未保存草稿并在 A 卡片打上“未保存”标记，绝不将 A 的编辑值带入 B；若当前页存在未保存修改而试图导入新批次或切换主体时给出明确提示。
   - **CLI 批次导入接手**：左栏/顶栏支持直接打开 CLI 生成的复核包 JSON（或选择共享本地批次号），无缝延续中栏筛选与右栏人工修正。

### F-07 命令行批处理与 Harness 离线评测套件

1. **入口与前置条件**：
   - 入口 A：CLI 批量解析命令（`parse`：接收输入文件/目录/URL、记账主体、已有账单基准 JSON、输出路径及可选工作台复核包输出路径）。
   - 入口 B：CLI 评测命令（`eval`：运行内置 Harness 回归与多次稳定性测试）。
2. **分步操作与输入要求**：
   - **批处理命令反馈与交接约定**：
     - 控制台按文件逐项汇报：解析通道（远端 OCR / 表格解析 / 邮件递归 / 失败）、产出条数与待复核/失败告警摘要，并打印复核包路径或工作台直达提示供财务人员接手；
     - 退出码约定：`0` = 至少产出合法标准输出且未出现阻塞性执行崩溃（标准输出始终为合法 JSON），同时明确打印 `failed_files` 与 `pending_review_count`；传入 `--strict` 参数时，只要存在失败文件或待复核记录即返回非零退出码。
   - **Harness 评测套件（必须同时度量准确性、拦截率与稳定性）**：
     - 内置不少于 **10 组真值标注样本与对抗测试用例**：覆盖 4 份原题文件、`.xls`/`.xlsx`/`.doc`/`.docx` 金额已知自制标准样本、部分字段 `UPDATE`（如仅改 `PP -> CC` 及 `30 -> 40`）对比 V1/V2 双基准、双入口重复附件、`Credit Note` 负向冲减、含税总额对账、OCR `0/O` 与零总额不平拦截、无关记账主体拦截；
     - **双轨独立汇报（绝不混为一谈）**：
       1. **真值准确性与拦截指标**：JSON Schema 通过率、关键字段相对标准真值（Ground Truth）的精确匹配准确率（Field Exact Match / Amount & Currency Accuracy）、AR/AP 准确率、四态操作准确率、异常/冲突拦截召回率与误报率（保证“稳定提错”得不到高分）；
       2. **非确定性稳定性指标**：在真实 LLM 模式下按 $k$ 次重复执行统计 `pass@k` 与 `pass^k`（要求每次运行全字段与校验结果 100% 达标才计入 `pass^k`），并在离线测试模式下运行确定性规则+替身回归套件；
     - **交付物与实操启动验收**：提供可一键解包/克隆后按 README 启动的完整代码仓库、打包 ZIP 流程校验脚本，以及书面交付《Harness 工程设计与稳定性保障方案》与不少于 5 点兼具业务与技术深度的《补充思考与架构建议》。
3. **正常反馈与去向**：
   - 评测结束打印详细对比表、生成 JSON/Markdown 评测报告，并可在 Web 工作台“评测看板”抽屉加载真实最近一次评测结果（仅展示实际执行记录，无数据时提示请先运行评测，绝不伪造高分）。
4. **边界、异常与多区域联动状态**：
   - 真实 OCR 或真实 LLM 评测遇到网络不通、密钥缺失或限流时，如实输出 `UNVERIFIED` 与具体失败用例及错误原因，返回非零状态码，绝不自动切换替身伪装成真实联机通过。

## 7. 待决问题与技术备注

### 7.1 工程待决与边界配置项
- **本地二进制文件上传调用远端 OCR 的公网地址中转方案**：
  - 已明确外部 OCR 服务须接收可下载的公网文件 URL；对纯内网或本地上传文件的中转策略（优先直传用户提供的公网 URL；若本地启动时配置了对象存储预签名/临时公开静默中转基址则自动上传生成限时 URL；两者均未配置时仅允许用户显式勾选并打标本地安全兜底，且绝不伪冒远端 OCR 成功）将在架构设计环节确定可插拔适配器接口。

### 7.2 技术备注（供架构与开发阶段严格遵守）
1. **强制语言与框架**：后端与智能体编排必须基于 **Python** 与 **LangChain**（结合 LangGraph 状态机及 Pydantic v2 `with_structured_output` 强制结构化输出 + `uv` / `pyproject.toml` 依赖管理）。
2. **外部 OCR API 契约与网络特性**：
   - 请求接口：`POST https://gateway.pltplt.com/ai/process`
   - 请求体：`{"file": "<公网URL>", "task": "orderChange", "callBack": "", "taskType": ""}`，超时 `(10, 300)`。
   - **已实测关键事实**：本机存在系统代理时经代理访问 `gateway.pltplt.com` 会出现 SSL EOF，**配置直连（绕过 HTTP 代理）可稳定返回 HTTP 200**，返回包含 `data.list[].{fileType, invoiceNumber, mblNumber, shipper, consignee, ctrList, chargeList, hold, other, suspicious, page_index}` 与 `pages_split`。封装客户端时须支持显式直连/代理开关，并充分利用网关已提取的 `chargeList`、`suspicious` 等结构字段与页码信息参与交叉校验。
3. **跨平台文档解析选型边界**：在技术选型中采用不依赖本地桌面 Office 或 LibreOffice 的跨平台解析方案（如纯 Python `xlrd`/`openpyxl` 解析 `.xls`/`.xlsx`，`legacy-doc`/`python-docx` 解析 `.doc`/`.docx`，并搭配文本层与 OCR 交叉对照验证）。
